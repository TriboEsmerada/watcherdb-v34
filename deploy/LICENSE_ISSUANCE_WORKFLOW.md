# License Issuance Workflow

**Audience:** WatcherDB vendor team (sales engineering + ops)
**Scope:** Procedimento normal de emissão de `license.dat` para clientes
**Frequency:** Por contrato — typical 5-50/year
**Risk level:** 🟢 BAIXA — procedimento rotina, scoped per-customer, não afecta deploys existentes

> Para procedimentos catastróficos (key rotation), ver `KEYPAIR_ROTATION_RUNBOOK.md`.
> Para procedimentos de revogação, ver secção §6 deste doc.
> Para procedimentos de renovação anual, ver secção §7 deste doc.

## §1 Workflow overview

```

│ Cliente assina  │────▶│ Cliente envia   │────▶│ Vendor emite    │
│ contrato + tier │     │ HW fingerprint  │     │ license.dat     │
└─────────────────┘     └─────────────────┘     └────────┬────────┘

                        │ LICENSE_OK      │
                        └─────────────────┘
```

## §2 Pré-requisitos do cliente (antes de pedir license)

Cliente deve ter:

1. **Contrato assinado** — tier escolhido (Standard / Pro Standard / Pro Enhanced Sovereign / Pro Enhanced Banking) + período (default 1 ano)
2. **WatcherDB MSI instalado** no servidor target (mas ainda não a correr — strict mode rejeita sem license, grace period 60d kicka in se enforcement disabled)
3. **Hardware fingerprint** colectado (IDs do servidor onde será ATIVADA a license)

### Como cliente colecta fingerprint

Vendor envia ao cliente a saída de `python deploy/license_cli.py fingerprint`:

```powershell
# PowerShell elevated no servidor cliente
$bios = (Get-CimInstance Win32_ComputerSystemProduct).UUID
$cpu  = (Get-CimInstance Win32_Processor).ProcessorId
$host = [System.Net.Dns]::GetHostName()
Write-Host "BIOS UUID:   $bios"
Write-Host "CPU ID:      $cpu"
Write-Host "Hostname:    $host"

# Para banking strict mode (V6) — adicionar SQL SERVERNAME
sqlcmd -E -S <SQL_INSTANCE> -Q "SELECT @@SERVERNAME"
```

Cliente envia 3-4 valores ao vendor via email seguro.

## §3 Vendor decisions (antes de emitir)

### 3.1 Edition

Confirmar do contrato. Mapping:

| Contrato | Edition string |
|---|---|
| WatcherDB Standard | `standard` |
| WatcherDB Pro (Standard) | `pro_standard` (legacy alias `pro` aceite por V5) |
| WatcherDB Pro Enhanced Sovereign | `pro_enhanced_sovereign` |
| WatcherDB Pro Enhanced Banking | `pro_enhanced_banking` |

### 3.2 Industry / Regulatory regime

Para clientes Pro Enhanced (sovereign + banking), industry + regimes determinam features banking-specific gating + audit retention.

**Presets disponíveis** (`deploy/license_cli.py` → `INDUSTRY_PRESETS`):
- `banking_pt` — banking + GDPR + EBA + BdP + DORA + SOC2
- `banking_eu` — banking + GDPR + EBA + DORA + SOC2 (sem BdP)
- `healthcare_us` — healthcare + HIPAA + SOC2 + ISO27001 (sovereign)
- `retail_eu` — retail + GDPR + PCI-DSS (pro_standard)
- `generic_pt_pro` — generic + GDPR (pro_standard)

Se cliente não cabe em preset, especificar manualmente:

```bash
--industry banking --regimes GDPR EBA BdP DORA SOC2
```

### 3.3 Expiry date

Default: 1 ano após emissão. Banking enterprise: 2-3 anos típico (ver SOC 2 Type II / DORA contract).

### 3.4 License ID

UUID v4 — **gerado automaticamente** se não passes `--license-id`. CLI gera + imprime na resposta. Vendor regista license_id no CRM (necessário para revocation futura).

## §4 Emissão (vendor steps)

### 4.1 Single license

```powershell
python deploy/license_cli.py issue `
    --customer-id <UUID> `
    --customer-name "Cliente XYZ" `
    --preset banking_pt `
    --bios-uuid AABBCCDD-1111-2222-3333-444455556666 `
    --cpu-id BFEBFBFF00090672 `
    --hostname BANKXYZ-SQL01 `
    --sql-servername "SQLBANKPRD01\PROD" `
    --expires 2027-04-25 `
    --out .\licenses\cliente_xyz.lic
```

Output esperado:
```
✓ Issued: licenses\cliente_xyz.lic
  customer_id  : <uuid>
  customer_name: Cliente XYZ
  edition      : pro_enhanced_banking
  expires      : 2027-04-25
  industry     : banking
  regimes      : ['GDPR', 'EBA', 'BdP', 'DORA', 'SOC2']
  license_id   : <auto-generated-uuid>
  features ON  : 53/53
  sql_servername: SQLBANKPRD01\PROD (banking-strict fingerprint)
```

### 4.2 Batch (multi-customer)

CSV format:
```csv
customer_id,customer_name,edition,expires,bios_uuid,cpu_id,hostname,industry,regimes,sql_servername
banco-001,Banco A,pro_enhanced_banking,2027-04-25,AABB,CCDD,A-SQL,banking,GDPR;EBA;BdP,A-SQL\PROD
banco-002,Banco B,pro_enhanced_banking,2027-04-25,EEFF,1122,B-SQL,banking,GDPR;EBA;BdP,B-SQL\PROD
retail-001,Loja X,pro_standard,2027-04-25,3344,5566,X-SQL,retail,GDPR,
```

```powershell
python deploy/license_cli.py batch `
    --input customers_q2_2026.csv `
    --output-dir .\licenses\q2_2026\
```

### 4.3 Vendor-side audit

Cada license emitida deve ser registada no CRM com:
- license_id (UUID)
- customer_id + customer_name
- edition + expires_at + issued_at
- HW fingerprint (truncated SHA256 dos 4 components)
- Email contacto técnico cliente
- PO/contract reference

## §5 Distribuição (vendor → cliente)

### Canal seguro obrigatório

❌ **NUNCA enviar `license.dat` em:**
- Email não-encriptado
- Slack/Teams chat
- USB sem encriptação

✅ **Canais aceitáveis:**
- Email com PGP/S-MIME
- Vendor portal (HTTPS + auth)
- Encrypted USB entregue presencialmente
- Secure file transfer (SFTP, Microsoft Compliance Manager, etc.)

### Acompanhar com instructions cliente

Email exemplo:

```
Subject: WatcherDB License — Cliente XYZ — Edition Pro Enhanced Banking

Olá,

Anexo o ficheiro `cliente_xyz.lic` correspondente ao contrato XYZ-2026-001.

Detalhes:
- Edition: Pro Enhanced Banking
- Servidor activo: BANKXYZ-SQL01 (BIOS UUID terminado em ...4666)
- Válido até: 2027-04-25
- License ID: <uuid>

Para deploy:

1. Backup da license actual (se aplicável):
   Copy-Item C:\ProgramData\WatcherDB\license.dat C:\ProgramData\WatcherDB\license.dat.bak

2. Colocar nova license:
   Copy-Item cliente_xyz.lic C:\ProgramData\WatcherDB\license.dat -Force

3. Restart services V6:
   Restart-Service WatcherDBWebServiceV6
   Restart-Service WatcherDB-V6-Hybrid

4. Verificar Event Log (Application source "WatcherDB"):
   - 1000 LICENSE_VALIDATION_OK = sucesso
   - 1001 LICENSE_VALIDATION_FAILED = problema, contactar vendor
   - 1002 LICENSE_EXPIRY_WARNING = warning expira <30d (informativo)

Em caso de problemas:
- Verificar fingerprint correcto (BIOS UUID + CPU ID + Hostname matches)
- Confirmar que public key está em C:\ProgramData\WatcherDB\ed25519_public.pem
- Logs em C:\ProgramData\WatcherDB\logs\

Cumprimentos,
[Vendor team]
```

## §6 Revogação (sub-procedimento)

Cenários típicos:
- Cliente cancela contrato antes de expiry
- License compromised (HW migrated sem re-license, suspeita fraud)
- Re-emit (vendor anula license antiga após emitir nova com alterações)

### Vendor steps

```powershell
# Adicionar license_id ao CRL (cria CRL se primeira revocation)
python deploy/license_cli.py revoke `
    --license-id <uuid-da-license-a-revogar> `
    --reason "Contract terminated 2026-04-25 — customer XYZ" `
    --crl .\revoked_licenses.json
```

CRL é signed com mesma master key que license.dat. Cumulative — preserva revocations anteriores.

### Distribuição CRL

Mesmo canal seguro que license.dat. Cliente coloca em `C:\ProgramData\WatcherDB\revoked_licenses.json` + restart services.

**Behavior pós-deploy:**
- Service tenta startup → CRL detected → license_id check
- Se license_id revocada: Event Log 1001 + service refuses start (strict mode)
- Audit trail: vendor + cliente têm registry da revocation timestamp + reason

⚠️ **CRL é fail-open** — se CRL ausente OR signature invalid, service arranca sem revocation check. Razão: avoid bricking clientes em distribution failures. Trade-off aceitável porque vendor controls signature key — cliente não pode forjar CRL para "esconder" revocations.

## §7 Renovação anual

Cenário: license expira em <30d (Event Log 1002 LICENSE_EXPIRY_WARNING).

### 7.1 Notificação proactive

Vendor monitor expiry dates no CRM. 60d antes de expirar:
- Email cliente com renewal quote
- Confirmar tier mantém-se OU upgrade
- Confirmar HW fingerprint não mudou (servidor migrado etc.)

### 7.2 Re-emit license

Mesmo procedimento §4 mas **MANTER `license_id` igual** (continuity em audit logs):

```powershell
# Reuse license_id existente da CRM
python deploy/license_cli.py issue `
    --customer-id <UUID> `
    --customer-name "Cliente XYZ" `
    --preset banking_pt `
    --bios-uuid <SAME-AS-BEFORE> `
    --cpu-id <SAME> `
    --hostname <SAME> `
    --sql-servername <SAME> `
    --expires 2028-04-25 `
    --license-id <SAME-UUID-FROM-CRM> `   # IMPORTANT: reuse para continuity
    --out .\licenses\cliente_xyz_2028.lic
```

### 7.3 Cliente deploy

Mesmo §5 — overwrite + restart services. Sem downtime se restart staged em maintenance window.

⚠️ **Caveat backward compat:** se HW MUDOU desde license original (ex: cliente migrou servidor), fingerprint atual ≠ fingerprint license antiga. Renovação precisa de novos HW IDs do cliente.

## §8 Troubleshooting

### Cliente reporta "service não arranca pós-instalação"

1. Pedir Event Log 1001 (LICENSE_VALIDATION_FAILED) — contém `reason=<ExceptionType>`
2. Reasons comuns:
   - **LicenseMissingError** → cliente esqueceu colocar license.dat. Confirmar path.
   - **LicenseFingerprintError** → HW IDs não match. Re-collect fingerprint atual no servidor + comparar com license original.
   - **LicenseSignatureError** → license corrompida (transferência mal sucedida) ou public key errada. Re-enviar ambos.
   - **LicenseTierMismatchError** → license para tier diferente do build. Verificar edition vs MSI installed.
   - **LicenseRevokedError** → license revocada. Confirmar com CRM se foi intencional.
   - **LicenseExpiredError** → expiry date passada. Renovar (§7).

### Cliente em grace period (60d)

Event Log 1003 LICENSE_GRACE_PERIOD_ACTIVE indica cliente sem license válida ainda. Vendor deve emitir + entregar dentro window.

### Cliente reporta features Pro não disponíveis

Confirmar tier no license.dat (`payload.edition`) corresponde ao tier do build. Features-level — verificar `payload.features` tem flags ON apropriadas. Use `--features-json` override em re-issue se necessário.
